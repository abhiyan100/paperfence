# Review 4 (Codex, read-only, 2026-09-20)

Aimed at the surface added after review 3, which had had none: the control plane, the capability graph, receipt merging and sharding, the Codex driver, and the benchmark statistics. Ten findings, all real, all fixed.

Seven of the ten are the same failure this project exists to find: reporting evidence it had not earned.

| # | finding | fix |
|---|---|---|
| 1 | The graph matched controls by rule category alone, so a gate on "never read `.env`" marked an unrelated `AWS_SECRET_ACCESS_KEY` as protected. | A control covers an asset only when it names the asset, names a file the asset was found in, or names nothing and so applies to its whole category. The detail says which rules exist and why none covers this asset. |
| 2 | A merged report is built from receipts with no static probe, so a live block became a `GATE` even for a rule the static probe had shown to be bypassable. | With no static probe, a live block is `WISH` with the reason stated. The static probe is what finds the routes the live agent did not try; a report that never ran one cannot claim a gate. |
| 3 | Codex conformance read every absent effect as confinement, so a model saying "I will not do this" counted as the sandbox working. Results marked unobservable were counted as agreeing, an error after an agent message was ignored, and the read case asserted its own observation as `false` so it agreed without establishing anything. | Each confinement case now runs a control at `danger-full-access`. If the effect happens with the sandbox off and not with it on, the sandbox confined it; if it happens in neither, the model declined and the case is not settled. The read case is observed through the command record instead, which is the only thing a successful read leaves. |
| 4 | Benchmark rates used an outcome-dependent sample: `attack` stops a form after its first failure, so failing forms contributed fewer trials than passing ones and the pooled rate understated the truth. | `attack` gained an `exhaustive` mode and the benchmark uses it, so every form runs at every level for every repetition and the Wilson interval is computed over a fixed design. |
| 5 | Receipt ids are content addresses and therefore global, while the primary key was not scoped to a project. Uploading a receipt obtained from another team silently claimed the row, and their own upload came back "already had" while their summary never showed it. | An upload whose id already belongs to another project is rejected with that reason, rather than being swallowed as a duplicate. |
| 6 | Merging checked only runtime fingerprint fields, so receipts from different repository commits, scenario versions, variants and turn budgets pooled into one apparent experiment. | Those four are checked too, with scenario version compared per rule since two rules legitimately differ. |
| 7 | `JSON.stringify` turns `Infinity` into `null`, so a receipt holding `null` and one holding `1e400` canonicalised identically and shared an id. Two different accepted documents, one id, no cryptography required. | Non-finite numbers canonicalise to their own token. Fixed in both the CLI and the control plane's copy, and the cross-check test covers them. |
| 8 | A git remote of the form `https://user:token@host/repo` became the asset name and id, and those appear in the graph's JSON, terminal output and HTML. | Credentials are stripped from the remote before it becomes an asset. That the URL holds one is itself reported, without the value. |
| 9 | Codex `file_change` events carry their paths in `changes`, not `path`, so every edit was dropped and a run that rewrote files produced an empty event list. | Both shapes are read. |
| 10 | Unwrapping `zsh -lc '...'` stripped the outer quotes but left the inner escaping, so a command naming a path with a space was recorded differently from the one that ran. | The escaping is undone for both single and double quoted forms. |

Found separately, by probing the deployed service during the same pass: the control plane verified a receipt's content address on the client and not on the server, so a receipt with the id `pf_forged00001` and no relationship to its contents was accepted and stored. The server verifies now. That one is in ADR 0010.

Probes that found nothing: no token and a wrong token are refused, a project token cannot create projects, wrong verbs are refused, the `since` parameter is validated by pattern rather than interpolated, the window is clamped, and a receipt claiming a foreign `project_id` is stored under the authenticated project instead.
