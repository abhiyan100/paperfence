## Direction

**The problem is real. I would not trust the current grades as security guarantees.** I would use paperfence to find candidate gaps, then inspect the evidence.

I read the requested files, including the Docker and runner files added during this review. Typechecking passed. I reproduced permission, hook, and assertion failures with harmless commands and in-memory harnesses; I did not execute a live adversary or container.

My top three concerns:

1. **The evaluator can damage the machine running it.** Host mode is an adversarial agent with broad permissions and a regex guard. That is a release blocker.
2. **GATE overstates the evidence.** Blocking two example commands proves those examples were blocked. It does not prove the rule is enforced. Worse, `attack` skips static gates, preventing the adversary from challenging that conclusion.
3. **The experiment changes the policy it claims to measure.** It automatically approves permission requests, omits local settings, uses fixture-specific objectives, and attributes unrelated blocks to the rule under test.

Static probing → adversarial testing → suggested hardening is a sound workflow. The grades need separate dimensions: **mechanism found, probes blocked, violation observed, coverage incomplete, run failed**. WISH and BROKEN can both describe the same rule; they are not mutually exclusive properties.

Auto-hardening also changes meaning: “ask before publishing” becomes “never publish”; “don’t weaken tests” becomes “don’t edit tests.” Show those policy changes explicitly.
